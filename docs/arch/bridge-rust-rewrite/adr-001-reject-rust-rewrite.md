# ADR-001（bridge-rust-rewrite）：暂不以 Rust 重写 connector

- **状态**：accepted（否决，附复查触发条件）
- **日期**：2026-11-11
- **上下文**：[`context.md`](./context.md) —— 实测数据与瓶颈定位
- **相关**：[`lark-rust-sdk-survey.md`](./lark-rust-sdk-survey.md) —— Rust SDK 生态调查

## 背景

有人提出用 Rust 重写 `lark-channel-bridge`（TypeScript 的飞书 ↔ 本地 CLI agent 桥），
理由是「效率更高、资源占用更少」。

本 ADR 记录**为什么不在此刻做**，以及**什么条件下应该重新评估**。

## 决策

**暂不重写。** 保持 TypeScript 实现。

## 理由

### 理由 1：瓶颈不在 bridge，实测占比 <0.1%

实测链路耗时（详见 context.md）：

| 环节 | 实测 |
|---|---|
| 模型调用（YuShan 一个回合） | **6.74s / 7.99s / 19.20s** |
| YuShan 进入 runtime | ≈2.5s |
| bridge 处理一条消息 | **毫秒级** |

bridge 的总耗时占比 **不到 0.1%**。用 Rust 优化这 0.1%，用户不可感知。

### 理由 2：Rust 省不了本项目真正的开销

YuShan 自身就是 Rust 程序，可作为对照：

| 场景 | 实测 |
|---|---|
| `--version`（不装配 runtime） | **0.00s** |
| 进入 runtime（装工具表、扫 skill、连模型） | **≈2.5s** |

**Rust 省的是进程启动，不是架构级装配。** bridge 换成 Rust 后，它自己的装配成本
（加载 profile、解析事件、构建卡片）一分不省。

### 理由 3：飞书官方无 Rust SDK，协议层要靠社区

官方服务端 SDK 只支持 Go / Python / Java / NodeJS / PHP，**无 Rust**。

当前 `@larksuite/channel` 由 `larksuite` 官方组织维护。换 Rust 后，WS 长连接可用的
最佳选择是 `larksuite-oapi-sdk-rs`——**12 star / 4,266 下载**；下载量最高的
`open-lark`（33k）恰恰 WS 仍标「计划中」。详见 SDK 调查文档。

这等于用约 60 MB 内存，换掉官方维护的协议层，承担 schema 漂移与单点依赖风险。

### 理由 4：收益不抵代价

| 乐观收益 | 值 |
|---|---|
| 常驻内存 | 省约 60 MB（50–80 MB → 10–20 MB） |
| 消息延迟 | 毫秒 → 亚毫秒（不可感知） |
| CLI 冷启动 | ~100 ms → ~5 ms |

| 代价 | 量级 |
|---|---|
| 重写 WS 协议层 | 握手、心跳、重连退避、schema 兼容 |
| 重写卡片构建 | 12 个文件 |
| 重写整体 | 123 文件 / 26,641 行 |
| 丢失官方 SDK 支撑 | 无 |
| 双语言维护 | TS + Rust + YuShan |

### 理由 5：已有更便宜的解法未穷尽

在考虑重写前，以下做法成本极低且未实施：

1. 调低 `ProcessPool` 并发上限
2. Web 控制台（`src/ui/*`）延迟加载
3. 减少 49 处定时器中的轮询类（如 `src/meeting/manager.ts` 的轮询降级路径）
4. 重计算需求单独写 Rust 侧车，bridge 仅做 IPC

第 4 条与现有架构天然一致：bridge 已通过 `--json` NDJSON 驱动 Rust 的 YuShan。

## 被否决的替代方案

### 方案 A：全量重写为 Rust

**否决**，理由 1–4。收益集中在内存，代价集中在协议层风险。

### 方案 B：只把协议层换成 Rust 侧车

即 bridge 保留 TS，另起一个 Rust 进程专管飞书 WS 长连与 HTTP。

**否决**，因为：

- 这层**本来就不是瓶颈**（空闲连接，非 CPU 密集）
- 当前 SDK 工作正常且官方维护
- 引入进程间协议、双份状态管理、两处部署
- 收益仍只是那 60 MB，而复杂度显著上升

此方案若将来重启，触发条件见下。

### 方案 C：混合——Rust 做重计算，TS 做胶水

**未否决，是正确方向**，但**当前无重计算需求**，所以暂不实施。

这是本 ADR 倾向的方案形态：语言分工按「计算密度」切，而非按「觉得 Rust 快」切。

## 复查触发条件

满足**任意一条**即应重新评估，不必重新论证全部前提：

1. **内存成为硬约束**：需部署在 ≤128 MB 的容器 / 树莓派，44.7 MB 的 Node 基线不可接受
2. **事件频率升量级**：从「每分钟几条」变为「每秒几十条」，毫秒级开销累积成真问题
3. **出现真正的重计算需求**：本地音视频转码、本地模型推理、大文件处理——此时按方案 C
   写 Rust 侧车，**不重写 bridge**
4. **Rust 飞书 SDK 成熟**：`larksuite-oapi-sdk-rs` 或 `open-lark` 达到「WS 完善 + 有官方
   或大厂背书 + 下载量 10 万级」，届时理由 3 的前提消失
5. **官方推出 Rust SDK**：直接重估

## 决策影响

- **不产生代码改动**
- `docs/arch/yushan-adapter/` 的工作**不受影响**，继续按该目录设计推进
- 若有人在未来再次提出同一提议，应先读本 ADR 与 `context.md`，避免重复实测

## 遗留

- 收益数字为**估算**，基于 Node 空进程基线 44.7 MB 外推，未实际构建 Rust 原型测量
- 若复查触发条件 1 或 2 成立，应实测一个最小 Rust 原型后再定，而非沿用本 ADR 估算
